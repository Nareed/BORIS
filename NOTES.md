## 2. In-memory event model

Whole project lives in `self.pj` (set in `load_project`, [core.py:2797](boris/core.py:2797)). Each observation ([observation_operations.py:1064](boris/observation_operations.py:1064)) has an `"events"` list. **Confirmed against the real fixture** ([tests/files/test.boris:39-53](tests/files/test.boris:39)):

```json
"events": [
  [22.425, "", "p", "", ""],
  [199.96, "", "p", "", ""]
]
```

Each event is a plain Python **list** (`[time, subject, code, modifier, comment]` for LIVE/legacy; MEDIA adds a trailing frame index, IMAGES adds trailing image index + path — [config.py:324-343](boris/config.py:324)). `time` is a `decimal.Decimal` in memory, plain JSON number on disk. Field-index constants: `EVENT_TIME_FIELD_IDX=0`, `EVENT_SUBJECT_FIELD_IDX=1`, `EVENT_BEHAVIOR_FIELD_IDX=2`, `EVENT_MODIFIER_FIELD_IDX=3`, `EVENT_COMMENT_FIELD_IDX=4` ([config.py:349-354](boris/config.py:349)).

**⚠ STATE event pairing — no explicit start/stop flag.** A state behavior (`"type": "State event"` in the ethogram, e.g. code `"s"`) is stored as **two ordinary event rows with the identical code**; BORIS pairs them by chronological order per (subject, code) — first occurrence = start, second = stop, odd count = UNPAIRED. Confirmed in the fixture, observation `"2 video"` ([tests/files/test.boris:814-828](tests/files/test.boris:814)):
```json
"events": [
  [10.0, "subject1", "s", "", ""],
  [170.0, "subject1", "s", "", ""]
]
```
and in observation `"modifiers"` ([tests/files/test.boris:722-771](tests/files/test.boris:722)), where a modifier value round-trips across a start/stop pair (both rows of a pair carry the same modifier: `"m1"`/`"m1"`, `"None"`/`"None"`). **Implication for the importer (FR-2/FR-6):** when converting a CSV START+STOP pair into BORIS events, insert two list entries with the same behavior code, the same subject, the same modifier, at their respective times — do NOT invent a separate "is_start" field. Insertion order across the whole list must keep every (subject, code) pair's start before its stop in time order (`bisect.insort`, see §3, already guarantees overall time-sortedness, but cross-check pairing after insert — BORIS's own UNPAIRED detection is the safety net).

Ethogram entry shape, cross-checked against both files — **`test.boris`** has `{"type": "Point event"|"State event", "key", "code", "description", "category", "modifiers": {...}, "excluded", "coding map"}`; the real project (`test-projects.boris`) has the same fields **plus a `"color"` field** (e.g. `{"type": "State event", "key": "s", "code": "Sniff food outside", "description": "", "color": "", "category": "", "modifiers": "", "excluded": "", "coding map": ""}`) and — importantly — **`"modifiers"` is `""` (empty string) when no modifier set is configured, not `{}`**. Don't assume `modifiers` is always a dict: treat it as "falsy → no modifiers" and only index into it as a dict when it's actually non-empty (`test.boris`'s modifier-bearing entries do use the `{"0": {"name", "type", "values": [...]}}` shape shown in §2, so that structure is real, just not the *default*). Subject entry shape, same in both files: `{"key", "name", "description"}` — **no color field on subjects in either file**, which matters for M4: the spec's per-subject color-coding (§7, active-subject highlighting, color legend) has no home in BORIS's own project schema, so the importer/UI will need to invent its own subject→color assignment (e.g. a fixed palette keyed by subject index), not read one from the project.

## 3. Key calls: adding an event, setting its subject

Appending happens in [boris/write_event.py:37](boris/write_event.py:37), `write_event(self, event: dict, mem_time: dec)`:
- LIVE/MEDIA: `bisect.insort(self.pj[OBSERVATIONS][obsId][EVENTS], [mem_time, subject, code, modifier_str, comment])` ([write_event.py:496-505](boris/write_event.py:496)) — keeps the list time-sorted on insert.
- IMAGES: `.append(...)` then explicit `.sort(...)` ([write_event.py:507-514](boris/write_event.py:507)).
- Editing an existing row overwrites `EVENTS[event["row"]]` in place ([write_event.py:456-493](boris/write_event.py:456)).
- After any change: `self.load_tw_events(self.observationId)` ([write_event.py:517](boris/write_event.py:517)) refreshes the events widget (§1).

**Subject on a new event**: `self.currentSubject` (string, `""` = none) is set only via `update_subject(subject)` ([core.py:1631](boris/core.py:1631)). A coded-behavior event dict built by `full_event(self, behavior_idx)` ([core.py:4763](boris/core.py:4763)) is a copy of the ethogram entry and carries **no** `"subject"` key. In `write_event`:
```python
# write_event.py:120
subject = event.get(cfg.SUBJECT, self.currentSubject)
```
so a freshly-coded event's subject always falls back to `self.currentSubject`.

**⚠ Correction (M2): the importer must NOT call `write_event()`.** Reading the whole function (not just the append lines above) shows it's a complete live-coding state machine, not a plain appender: it infers state open/close by toggling against `util.get_current_states_modifiers_by_subject(...)`, pops up a **modal** `select_modifiers.ModifiersList(...).exec_()` per call whenever the matched behavior has modifiers configured ([write_event.py:278-284](boris/write_event.py:278)), and touches `self.dw_player[0].player...` assuming a live player is attached ([write_event.py:95](boris/write_event.py:95), [write_event.py:266](boris/write_event.py:266)). Calling it in a loop over hundreds of CSV rows would pop up hundreds of dialogs and could crash outright when there's no player. `boris/model_import.py`'s `insert_events()` instead builds rows directly with the exact list shape `write_event` itself uses for a plain "add event" (the same `bisect.insort` calls at [write_event.py:496-505](boris/write_event.py:496)) — `[time, subject, code, modifier, comment]` for LIVE, plus a trailing `cfg.NA` frame-index sentinel for MEDIA (matching `frame_idx = event.get(cfg.FRAME_INDEX, cfg.NA)` at [write_event.py:131](boris/write_event.py:131)) — then does **one** batched `self.load_tw_events(obs_id)` + `self.project_changed()` call at the end instead of one per row.

## 4. How the ethogram and subject list are read

On project load, `project_functions.open_project_json(...)` ([project_functions.py:1336](boris/project_functions.py:1336)) does `json.loads(...)`, then `util.convert_time_to_decimal(pj)` ([utilities.py:416-437](boris/utilities.py:416)) walks every event and converts JSON time numbers back to `Decimal`. `MainWindow.load_project(...)` ([core.py:2785](boris/core.py:2785)):
```python
self.pj = dict(pj)
self.load_behaviors_in_twEthogram([...pj[cfg.ETHOGRAM][x][cfg.BEHAVIOR_CODE]...])  # core.py:2800
self.load_subjects_in_twSubjects([...pj[cfg.SUBJECTS][x][cfg.SUBJECT_NAME]...])    # core.py:2801
```
`pj[ETHOGRAM]` (JSON key `"behaviors_conf"`) and `pj[SUBJECTS]` (JSON key `"subjects_conf"`) are dicts keyed by an arbitrary string index (`"0"`, `"1"`, …) — **for the importer, iterate `.values()` and match on the `code`/`name` field, not the dict key.** `load_subjects_in_twSubjects` ([core.py:4487-4509](boris/core.py:4487)) also rebuilds `self.subject_name_index` (subject name → pj-key), reusable for the importer's subject lookups instead of re-deriving it.

## 6. Modal dialogs — pattern to follow for confirm/mapping prompts

Two patterns, both ending in PySide6's `.exec_()`/`.exec()` (blocks until closed, returns `Accepted`/`Rejected`):

- **Custom `QDialog` subclass**, built then `.exec_()`'d by the caller — use this for the **overwrite-confirmation** and **behavior/subject map-or-add** dialogs (FR-4, FR-5, FR-11), since they need to show data and return structured results. Model: `select_modifiers.ModifiersList(QDialog)` ([select_modifiers.py:45](boris/select_modifiers.py:45)), invoked from [write_event.py:278-284](boris/write_event.py:278):
  ```python
  modifiers_selector = select_modifiers.ModifiersList(code, modifiers_dict, currentModifiers)
  r = modifiers_selector.exec_()
  if r:
      selected_modifiers = modifiers_selector.get_modifiers()
  ```
  Same shape: `edit_event.DlgEditEvent` ([edit_event.py:43](boris/edit_event.py:43)), `observation.Observation` ([observation.py:101](boris/observation.py:101)).
- **Module-level function** building a dialog internally, returning plain data — use this for a simpler one-off like the **file picker** (a `QFileDialog.getOpenFileName(...)` call is enough, no custom class needed). Model: `select_subj_behav.choose_obs_subj_behav_category(...)` ([select_subj_behav.py:36](boris/select_subj_behav.py:36)).

A plain `QMessageBox.question(...)` (Yes/No) is the natural choice for the overwrite-confirmation prompt specifically (FR-11) — simplest correct tool, no custom dialog class needed there.

## 7c. M4 — Fast subject assignment (implemented)

**⚠ Discovered before implementing, changed the design:** `tv_events` already had meaning for both click and double-click - plain click drives row *selection* (read by Edit event/Delete/Copy via `self.tv_events.selectionModel().selectedIndexes()`), and double-click already seeks the video player to that event's time (`tv_events_doubleClicked`, [core.py:5278](boris/core.py:5278), wired in `connections.py`). SPEC.md's original plan ("click to stamp, double-click to unassign", using `self.currentSubject`) would have silently reassigned an event's subject any time a coder - who commonly has a focal subject set during ordinary live coding, unrelated to import review - just clicked a row to select it for editing. Resolved by interview: a checkable **"Stamping mode" toolbar toggle**, default off. While off, `tv_events` behaves exactly as before this feature existed. While on, click stamps and double-click unassigns.

**⚠ Second correction, found via a failing test, not by inspection:** the original plan was to hash each subject name independently (`hashlib.md5(name) % palette_size`). Built it, wrote a test asserting 10 real project subject names would get 10 distinct colors, and the test failed - only 6 distinct colors out of 10 (pigeonhole: 10 names into an 18-slot palette collide often). Independent hashing is *stable* but not *distinguishing*, which was the actual point of having colors at all. Fixed by ranking each subject by its **position in the project's own subject list, sorted alphabetically** (`subject_color(name, subject_names)`), not hashing the name in isolation - guarantees no two subjects in the same project share a color (as long as subject count ≤ palette size; cycles beyond that). This is why `subject_color()`/`subject_qcolor()` take a `subject_names` list, and why `TableModel` now needs the project's subject-name list threaded into its constructor.

Collapsed the "map to existing" combo and "new name" field into a single `QStackedWidget` per row (3 columns total instead of 4: label / Action / Target), swapped by the Action combo - Skip shows a plain "(not needed)" label, Map shows only the existing-item combo, Add shows only the new-name field. Never displays information that isn't relevant to the row's current choice.

**UI polish from manual testing:** colors were too saturated/prominent, and both toolbuttons rendered as flat text rather than looking like buttons. Fixed: `subject_qcolor(..., alpha=FADE_ALPHA)` now applies a faded alpha (60/255) to every returned color (both the events-table rows and the `twSubjects` legend); row coloring in `TableModel` is now gated behind `stamping_mode_active` entirely (no color at all while the toggle is off, not just fainter); both toolbuttons get an explicit stylesheet (`BASE_BUTTON_STYLE`) so they read as buttons regardless of the active Qt style; the stamping toggle also swaps to `STAMPING_ON_STYLE` (green, bold) and its own text flips between "Stamping mode: ON"/"OFF" via `on_stamping_mode_toggled`, so the on/off state is unambiguous. Toggling mutates the live `TableModel` in place and emits `layoutChanged` rather than a full `load_tw_events()` reload.

**Follow-up:** "gone entirely while off" turned out to be the wrong call - user wanted colors still visible off-mode, just much fainter, not absent. `TableModel.data()` now picks between two alpha tiers (`event_stamping.FADE_ALPHA`=60 when on, `FADE_ALPHA_OFF`=18 when off) instead of returning `None` when off. `colorize_subjects_table` was later updated to use the same two-tier logic (initially it was a fixed `FADE_ALPHA` regardless of toggle state) - `on_stamping_mode_toggled` now re-colorizes `twSubjects` on every toggle, alongside the existing `tv_events` model refresh, so the legend and the events table always agree on fade level.

**⚠ Real bug, found via manual testing: double-click never unassigned, only single-click assign worked.** Root cause: `_apply_subject_to_selected_rows` called `self.load_tw_events(...)` after every stamp/unassign, which rebuilds the *entire* table model (`populate_tv_events` does `setModel(None)` then constructs and attaches a brand-new `TableModel`, [core.py:2263-2266](boris/core.py:2263)). A double-click's first press already fires Qt's `clicked` signal (that's `on_tv_events_clicked`, which stamps) *before* `doubleClicked` fires for the second press - and swapping the model mid-gesture invalidates the item identity Qt uses to recognize the second press as completing a double-click on the *same* row. So every attempted double-click was silently seen by Qt as two unrelated single clicks, and `doubleClicked` (and its unassign handler) never fired at all. Fixed: `_apply_subject_to_selected_rows` now mutates the raw project events list *and* the live model's own backing list (`model._data`, i.e. `self.event_state`) directly, then emits a scoped `dataChanged` instead of rebuilding - no model swap, so Qt's double-click detection is undisturbed. Trade-off: skips whatever else `load_tw_events`/`populate_tv_events` used to also refresh (e.g. the "current states" label) - acceptable here since stamping only changes which subject an existing event belongs to, not the event data BORIS actually saves/exports from.

## 10. Distribution — Windows installer for non-technical end users

Separate concern from the M0-M6 milestones above (packaging/branding, not the import feature itself), but landed in the same session/branch. The target users download BORIS from the official download page today, not git/pip — the deliverable is a normal double-click `Setup.exe`, no Python/git/terminal ever visible.

- **`boris/config.py`**: `programName` changed from `"BORIS"` to `"T4A-BORIS"` — propagates to the main window title and nearly every dialog/message-box title in the codebase (they all read `cfg.programName`). Rebranding, not just cosmetic: avoids user bug reports/support requests for fork-only features landing on the real BORIS maintainers.
- **`boris/core.py`**: `actionCheckUpdate_activated()` neutralized. Read the whole function before touching it (same discipline as the `write_event()` finding in §3) — upstream's flow pings `boris.unito.it` for the latest version and, if offered, downloads *upstream's source zip* and `shutil.copytree`s it directly over the running install. For this fork that would silently overwrite the model-import/stamping features with vanilla BORIS. Neutralized at the function level, not just by hiding the Help-menu action, since both the manual click and the built-in every-15-days auto-check (`config_file.py`) call this exact function. Menu item hidden too (`self.actionCheckUpdate.setVisible(False)`, added in `MainWindow.__init__`); dead `import zipfile` removed since nothing else in `core.py` used it.
- **`scripts/deployment/t4a_boris_windows_deployment.ps1`** (new) — adapted from upstream's own `scripts/deployment/windows_deployment.ps1` (their portable-zip builder: downloads a standalone Python, installs BORIS into it, strips unused PySide6 plugins, zips it). Two real deviations, both found by actually running it, not by inspection:
  - Upstream's script does `pip install boris-behav-obs` — the **public PyPI package**, i.e. vanilla upstream. Installing straight from this fork's local source dir instead hit a real setuptools failure: `Multiple top-level packages discovered in a flat-layout: ['boris', 'output']` — a stray empty `output/` directory at the repo root (removed) was enough to break package discovery. Fixed properly, not just by removing the directory: the script now builds a wheel first (`uv build --wheel`, matching this project's own `justfile` convention) and installs *that*, since a wheel is already a resolved file list and can't hit this class of bug regardless of what else is sitting in the repo root.
  - Upstream's script launches BORIS and blocks waiting for a human to close the window before continuing (fine for their interactive maintainer workflow). Since this also needs to run unattended, the smoke test here is non-blocking instead: `Start-Process`, wait a few seconds, confirm the process is still alive, kill it, continue - same pattern used throughout this session to verify launches without a human watching.
- **`scripts/deployment/t4a_boris_installer.iss`** (new) — Inno Setup script wrapping the portable build folder into a real installer: Start Menu entry, optional Desktop icon, Add/Remove Programs entry, uninstaller. Takes `MyAppVersion`/`BuildDir` as required `/D` defines (no sensible default - they change every rebuild). Launches via `pythonw.exe -m boris` (no console window). Inno Setup 6 installed via `winget install JRSoftware.InnoSetup`.
- **Built and verified end-to-end** (2026-09-03): wheel built from this exact branch → installed into a standalone Python 3.13.9 bundle → smoke-tested (launched, stayed running, closed cleanly) → compiled into `T4A-BORIS-9.14-setup.exe` (163MB) via `ISCC.exe`. The installer binary itself isn't committed (build artifact, fully reproducible from the two scripts above) - handed to the user directly. **Not yet installer-tested** - running `Setup.exe` needs interactive UAC approval, which only the user can provide.
- **Left open / not addressed**: no custom `.ico` (repo has no standalone icon file - BORIS's icon is a compiled Qt resource, not extracted here); no code-signing certificate for the installer (Windows SmartScreen will likely warn on first run - expected for an unsigned installer, not a bug); macOS/Linux equivalents not built (upstream's own Windows script was the only one adapted).
